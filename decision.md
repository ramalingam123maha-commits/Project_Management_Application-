# ProjectFlow – Decision Log

Every technical decision is recorded here with its context and rationale.
Format: **ID – Title** · Status · Decision · Reason · Alternatives considered.

| ID | Title | Status | Decision | Reason | Alternatives |
|----|-------|--------|----------|--------|--------------|
| D-001 | Overall style | Accepted | Monorepo with `backend/` and `frontend/`, communicating via REST/JSON | Simple to set up, review and deploy together | Separate repos, GraphQL |
| D-002 | Backend stack | Accepted | Java 17, Spring Boot 3.3, Maven | Requested stack; Java 17 LTS; Maven is the most common Spring build tool | Gradle |
| D-003 | Backend layering | Accepted | Controller → Service → Repository → Entity, with DTOs at the boundary | Separation of concerns; entities (e.g. password hash) never exposed | Exposing entities directly |
| D-004 | Database & migrations | Accepted | MySQL 8 with Flyway versioned migrations; `ddl-auto=validate` | Reproducible schema, safe upgrades | Hibernate auto-DDL |
| D-005 | Authentication | Accepted | Stateless JWT (HS256, secret from env var, short expiry) + BCrypt password hashing | Fits SPA + REST; no server sessions | Session cookies, OAuth2 provider |
| D-006 | Authorization | Accepted | Roles ADMIN / PROJECT_MANAGER / MEMBER via `@PreAuthorize`, plus ownership/membership checks in services | Role checks alone cannot prevent IDOR; server is the source of truth | UI-only checks |
| D-007 | Default role & first admin | Accepted | Self-registration creates MEMBER; initial ADMIN seeded from env vars; only Admin changes roles | Prevents privilege escalation at signup | Role chosen at registration |
| D-008 | Team membership | Accepted | PM/Admin adds existing registered users to a project by email | Keeps scope focused; no mail server required | Email invitation tokens (future) |
| D-009 | Error handling | Accepted | Global `@RestControllerAdvice` returning uniform `ApiError` JSON; no stack traces leaked | Consistent client handling, secure | Per-controller handling |
| D-010 | Validation | Accepted | Bean Validation on DTOs (authoritative) + Zod schemas in frontend (UX) | Defense in depth, instant feedback | Backend-only |
| D-011 | Frontend stack | Accepted | React 18 + TypeScript + Vite, React Router 6, TanStack Query, Axios, react-hook-form + Zod, Tailwind CSS | Requested stack; fast tooling; cached server state; responsive utility CSS | CRA, Redux, MUI |
| D-012 | Testing | Accepted | Backend: JUnit 5, Mockito, MockMvc with H2 test profile. Frontend: Vitest + React Testing Library | Fast, standard tooling; covers permission matrix and forms | Testcontainers (optional later) |
| D-013 | Local environment | Accepted | `docker-compose.yml` for MySQL + backend + frontend; `.env.example` with no real secrets | One-command setup; no secrets in git | Manual install only |
| D-014 | Process | Accepted | Every created item is logged in `Worklog.md`; every decision in `decision.md` | Requested by project owner for traceability | — |
| D-015 | Scaffold first | Accepted | Create all folders and empty files before writing any content | Requested by user; structure reviewable up-front | Build files incrementally |
| D-016 | Spring Boot version & JJWT | Accepted | Spring Boot 3.3.4 (Java 17 LTS baseline) and JJWT 0.12.6 | Modern Spring Boot 3.x with jakarta.* namespace; latest stable JJWT API with modular runtime artifacts | Spring Boot 2.x, Spring Authorization Server |
| D-017 | Database configuration & Flyway | Accepted | MySQL Hikari pool driven by environment variables (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`); Flyway runs on startup with `baseline-on-migrate: true`; Hibernate `ddl-auto: validate` | Ensures safe, reproducible schema changes without Hibernate altering production schemas; fully container- and 12-factor-ready | `ddl-auto: update`, manual SQL scripts |
| D-018 | Schema constraints & indexing strategy | Accepted | Explicit foreign keys (`ON DELETE CASCADE` for child records like tasks and project members; `ON DELETE SET NULL` for assignee; `ON DELETE RESTRICT` for project owner/reporter), check constraints on status/roles, and composite index `(project_id, status)` for task board queries | Maintains data integrity at the database engine level, prevents orphan records, and optimizes frequent Kanban board filter queries | Application-only constraints, unindexed foreign keys |
| D-019 | JPA domain model mapping | Accepted | Map entities with `@Table` pointing to Flyway V1 tables, `FetchType.LAZY` on all `@ManyToOne` relationships, `@EmbeddedId` with `@MapsId` for `ProjectMember`, `@Enumerated(EnumType.STRING)` for enums, and `@PrePersist`/`@PreUpdate` for timestamp auditing | Matches Flyway schema exactly for `ddl-auto: validate`, avoids N+1 eager loads, and guarantees proper ID association without external auditing dependencies | Eager fetching, auto DDL generation, numeric ordinal enums |
| D-020 | Spring Data JPA query optimization | Accepted | Use explicit JPQL `JOIN FETCH` queries for parent/child associations (`JOIN FETCH p.owner`, `JOIN FETCH t.assignee/reporter`) in repository methods instead of relying on lazy fetching during view serialization; keep queries parameterized | Eliminates N+1 query problems across API and dashboard calls while preserving lazy relationships on individual entity loads | Eager loading in entity mappings, multiple single-row select queries |
| D-021 | JWT validation strategy | Accepted | Token carries id/role/name claims, but the filter reloads the user from the DB on every request and builds authorities from the DB role | A role change or deleted user takes effect immediately instead of when the token expires | Trust token claims only (faster, stale roles) |
| D-022 | Security config choices | Accepted | CSRF disabled (stateless Bearer auth, no cookies); CORS limited to configured origins; default-deny (`anyRequest().authenticated()`); 401 body uses a fixed message so no internal details leak | Standard for JWT REST APIs; secure by default | Session cookies with CSRF tokens |
| D-023 | Admin seeding | Accepted | `AdminSeeder` runs at startup and creates the admin only if that email does not exist and no ADMIN exists yet; the default password in `application.yml` is for local dev only and must be overridden via `ADMIN_INITIAL_PASSWORD` in real deployments | Idempotent and never overwrites existing accounts | Flyway-inserted admin row (hash in git) |
| D-024 | DTO design using Java 17 records | Accepted | DTOs are immutable `record`s carrying Jakarta Bean Validation annotations (`@NotBlank`, `@Email`, `@Size`, `@AssertTrue`, `@Positive`); mapper is a stateless `@Component` | Built-in immutability, zero boilerplate (no Lombok needed), clear field-level validation contracts | Mutable POJOs, Lombok `@Data` |
| D-025 | Password length constraint | Accepted | `RegisterRequest.password` capped at 72 characters max (with >=8 min and letter+digit pattern) | BCrypt silently truncates passwords beyond 72 bytes; setting `@Size(max=72)` prevents surprising truncation behavior | Uncapped password length |
| D-026 | Auth behaviour | Accepted | Emails are trimmed and lower-cased before save and lookup; register returns 201 plus a token so the user is logged in immediately; login failures return one generic 401 for both unknown email and wrong password; a duplicate email returns 409 (also caught on DB unique-constraint races) | Avoids duplicate accounts differing by case, and avoids revealing which emails exist at login | Separate error messages for unknown user vs. bad password |
| D-027 | User management access | Accepted | `UserController` is annotated `@PreAuthorize("hasRole('ADMIN')")` at class level; an admin cannot change their own role (403) | Deny-by-default for every endpoint added to the class; avoids locking the system out of its last admin | Per-method checks; allowing self-demotion |
| D-028 | Project access rules | Accepted | Admin sees/manages all projects; a Project Manager manages only projects they own; Members and PMs can view projects they own or belong to. Creating a project also adds the owner as a member. Non-members get 404 (not 403) for a project they cannot see; members/PMs without manage rights get 403 | 404 avoids leaking which project ids exist; uniform membership rows simplify later task checks | 403 for everything; owner not stored as member |
| D-029 | Member removal | Accepted | The owner cannot be removed (409); removing a member sets their tasks in that project to unassigned | Keeps every assignee a current project member | Leave tasks assigned to removed users |
| D-030 | Update semantics | Accepted | `PUT /api/projects/{id}` replaces the whole project: omitted description and dates become null (status is kept if omitted) | Standard PUT meaning; the frontend form always sends all fields | PATCH-style partial update |
| D-031 | Task permissions | Accepted | Create/edit/assign/delete tasks: Admin or the owning PM. Status change: those two, or the task's assignee (members cannot move unassigned tasks). Viewing and commenting: anyone who can view the project. Tasks of projects a user cannot see return 404 | Matches the role matrix; members update only their own work | Any member can change any task status |
| D-032 | Assignment rule | Accepted | An assignee must be a project member or the owner (409 otherwise); assignment is its own endpoint `PATCH /api/tasks/{id}/assignee?assigneeId=` (omit to unassign) and also available via the task create/update body | Keeps assignees valid; simple call for the UI | Allow any registered user |
| D-033 | Comment deletion | Accepted | A comment can be deleted by its author or by someone who manages the project; comments are not editable | Moderation without an edit history | Allow edits; admin-only delete |
| D-034 | Dashboard scoping | Accepted | One endpoint, `GET /api/dashboard`, picks the scope from the caller's role: Admin = whole system, PM = projects they own and their tasks, Member = projects they belong to and tasks assigned to them. Overdue = due before today and not DONE. Upcoming deadlines = not DONE, due within 7 days, at most 10 | Matches the role matrix; one call keeps the frontend simple; the response shape is the same for every role | Separate endpoint per role |
| D-035 | Error responses | Accepted | One `@RestControllerAdvice` maps every exception to `ApiError`. Validation errors include per-field messages; DB integrity errors become a generic 409 and the real cause is only logged; unknown errors become a generic 500 | Consistent client handling, no information leakage | Per-controller handlers, default Spring error page |
| D-036 | Backend test strategy | Accepted | Unit tests mock repositories (Mockito); integration tests boot the full app on H2 (MySQL mode) with the real Flyway migration and security chain, creating uniquely named users per test so tests do not depend on each other | Tests the actual SQL schema and permissions without needing a MySQL server | Testcontainers MySQL (needs Docker) |
